# 使用者與登入規格

## 目的

這份文件定義 KhaiKang 第一階段的使用者與登入模型。
初版只做 Web，並使用本機帳號。LDAP、OIDC、SSO 與手機 App 登入都不在 v0.1 範圍內。

本文件同時定義：

- 共用的規格格式
- 權限模型基礎
- 之後延伸到專案管理與 AI 工作流時要沿用的設計原則

## 核心模型

第一階段必須支援：

- 本機使用者帳號
- Web-only 驗證
- 帳號類型區分
- 全域角色
- 專案角色
- 權限字串
- 透過 membership / assignment 表示授權範圍

### 帳號類型

系統中的帳號至少要區分兩種：

- `human`
- `ai_agent`

其中：

- `human` 代表真人使用者
- `ai_agent` 代表 AI 或自動化代理帳號

AI 帳號的設計原則如下：

- AI 帳號必須能進入稽核紀錄
- AI 帳號必須能對應到明確的執行身份
- AI 帳號不應直接沿用人類使用者的多角色模型
- AI 的能力應以任務設定或執行設定描述，而不是任意掛多個專案角色
- 所有 AI 動作都必須可追蹤到 `actor_id` 與 `actor_type`

人類帳號的設計原則如下：

- 人類帳號可以在不同專案掛上多個角色
- 同一個人可以同時擁有系統角色與多個專案角色
- 系統層與專案層的授權必須分開判斷

## 範圍

這份規格涵蓋：

- 第一次啟動時的管理員初始化
- 本機使用者登入
- 登出
- authentication ticket 到期
- refresh state 到期
- 密碼政策
- 最小權限邊界
- 帳號狀態管理

## 非目標

這一階段不包含：

- LDAP 整合
- OIDC / SSO 整合
- 手機 App 登入
- 社群登入
- Email 密碼重設
- 多因素驗證
- 委派式管理者建立流程

## 流程

### 第一次啟動管理員初始化

當系統第一次啟動，且尚未存在管理員帳號時，系統必須進入初始化模式。
初始化頁面由操作人員確認後呼叫一次性初始化 API。

在初始化模式下：

- 初始化 API 必須以 transaction 建立一組預設管理員帳號，帳號名稱固定為 `admin`
- 系統必須產生一組高強度的隨機初始密碼
- 密碼必須只在初始化 API 成功回應與初始化頁面顯示一次
- 初始密碼不得寫入啟動日誌
- 初始化完成後，密碼不得再以明文保存
- 管理員第一次成功登入後，必須強制更改初始密碼

初始化狀態會在第一個管理員建立完成後結束。

### 登入流程

使用者以以下資訊登入：

- 帳號名稱
- 密碼

系統必須：

- 驗證本機使用者帳密
- 拒絕停用或停權帳號
- 驗證成功後才建立有效登入狀態

## 狀態與規則

系統至少要支援以下使用者狀態：

- `active`
- `suspended`
- `disabled`

系統至少要支援以下角色：

- `System Admin`
- `User`

初版可以先採簡單權限模型，但角色檢查的設計要保留未來擴充空間。

### 權限模型

KhaiKang 的授權模型必須區分三件事：

1. 角色
2. 權限定義
3. 授權範圍

#### 全域角色

第一階段先支援以下全域角色：

- `System Admin`
- `User`

其中：

- `System Admin` 代表系統營運管理者，可執行帳號管理與系統層專案操作
- `User` 代表一般登入使用者

`User` 只代表可登入與基本系統存取能力，不包含系統管理權限。
使用者登入後的可見範圍仍由專案成員關係決定。
`System Admin` 不會因系統角色自動取得既有專案的讀取、設定、成員或 Issue 操作權限。

#### 專案角色

專案內部先使用系統預設角色，例如：

- `Owner`
- `Manager`
- `Contributor`
- `Reviewer`

專案角色只對指定專案有效，不等於系統管理員權限。

#### 權限定義

MVP 階段先使用系統固定提供的預設角色權限，不提供權限字串編輯或自訂角色能力。
權限本身與角色對權限的對應都由系統預設資料表管理，並透過 seed data 初始化。
MVP 階段不提供權限矩陣或角色權限的管理 UI。

#### 授權範圍

授權範圍用使用者與資源的指派關係表示。

例如：

- 使用者 A 在 Project X 是 `Owner`
- 使用者 A 在 Project Y 是 `Contributor`
- 使用者 B 只在特定專案有存取權

這表示同一個使用者在不同專案可以擁有不同角色與不同權限範圍。

#### 授權判斷原則

系統必須先依操作範圍選擇授權路徑：

1. 系統層操作：檢查帳號是否具備對應的系統角色權限。
2. 專案層操作：檢查帳號是否為目標專案的有效成員。
3. 專案層操作：取得該成員在目標專案的角色，再檢查角色對應權限。

`System Admin` 只能通過系統層權限檢查，不能略過專案層授權。建立專案是例外的系統層操作；建立完成後，建立者必須在同一個 transaction 內被加入新專案並指派為 `Owner`。

#### 設計原則

- `System Admin` 與專案角色要分開
- 專案範圍使用 membership 或 assignment 表示
- 專案層授權一律要求有效 membership，不因全域角色略過此條件
- `User` 只作為一般登入身份，不承載系統管理能力
- MVP 階段只使用系統預設角色，不提供權限調整功能
- AI 帳號的授權要以最小權限為原則
- AI 帳號不應依賴人類角色堆疊來獲得權限
- 之後若擴充更細粒度的範圍模型，也要沿用同樣的設計方式

## 安全與稽核

### 登入 session

Web 端使用 cookie-based authentication。

需求如下：

- authentication cookie 必須是 `HttpOnly`
- authentication cookie 必須是 `Secure`
- authentication cookie 必須明確使用 `SameSite=Lax`
- 前端 JavaScript 不得讀取 refresh credential

實作上應支援：

- 短效期的登入狀態
- 較長效期的續期機制

### Session 與 Token 政策

系統必須支援：

- 正常 API 使用的短效期 authentication ticket
- server-side 的登入狀態撤銷
- 登出時讓目前登入狀態失效

v0.1 建議政策：

- authentication ticket 狀態應自動到期
- persistent login 只有在使用者明確選擇 `Remember Me` 時才啟用
- server-side refresh state 必須可撤銷

實際有效時間長度屬於實作細節，但必須可設定。

### 登出

登出必須：

- 清除瀏覽器上的 authentication cookie
- 讓 server-side 的 refresh state 失效
- 登出後目前登入狀態不得再被重用

### 密碼政策

初版密碼政策至少要包含：

- 最小長度限制
- 存入資料庫前要先雜湊
- 不可保存明文密碼

v0.1 可選擇性支援：

- 密碼複雜度檢查

### 權限邊界

第一階段必須支援最小權限模型：

- `System Admin` 可以建立、查看、更新、停權、停用與恢復使用者
- `System Admin` 可以存取被授與的系統層級功能
- `user` 在專案模組完成後可以使用一般專案功能

專案層級的細部權限之後可以再擴充，但目前的模型不能阻礙未來做更細粒度的權限檢查。

### 帳號生命週期

系統必須支援以下帳號操作：

- 建立使用者
- 更新使用者資料
- 停權使用者
- 停用使用者
- 恢復使用者

由管理員建立本機人類帳號時：

- 帳號預設套用 `User` 系統角色
- 系統產生高強度隨機初始密碼，且只在建立成功回應顯示一次
- 初始密碼只保存雜湊，使用者第一次登入後必須修改密碼
- MVP 不提供從使用者管理頁面將一般帳號提升為 `System Admin`
- 具備 `account.update` 的管理者可在清單直接修改其他帳號的帳號名稱
- 帳號名稱與狀態異動使用版本欄位防止覆蓋其他管理者的更新
- 管理者不得從使用者管理清單修改或停用自己目前登入的帳號

當使用者被停權或停用時：

- 現有 session 必須失效，或在下一次驗證時被拒絕

### 安全要求

- 密碼必須使用現代單向雜湊演算法保存
- authentication cookie 必須使用 `HttpOnly`、`Secure` 與明確的 `SameSite` 設定
- 敏感資訊不得以明文寫入 log
- 登入流程必須適合瀏覽器使用
- 任何會改變狀態的 cookie-authenticated request 都要考慮 CSRF 防護

### 稽核要求

系統必須記錄以下稽核事件：

- 使用者建立
- 使用者更新
- 密碼變更
- 使用者停權
- 使用者停用
- 使用者恢復
- 登入成功
- 登入失敗
- 登出
- 管理員初始化完成

稽核紀錄至少要包含：

- `actor_id`
- `actor_type`
- 事件類型
- 事件時間
- 事件目標

其中 `actor_type` 用來區分人類操作與 AI / 自動化操作。

## AI 預留原則

第一階段只做人類工作流，但系統必須預留未來 AI 介入的介面與資料點。

設計原則如下：

- 人類操作仍以 UI 為主
- AI 必須有自己的帳號或執行身份
- AI 工作會預留 queue 或 job 入口
- 人類通知可走 webhook、站內通知或其他通知機制
- AI 相關動作必須可審核、可回退、可追蹤

這表示：

- 第一版不必真的實作完整 AI
- 但流程、資料結構與 hook 位置要先留好
- 之後補 AI 時，不應推翻整個工作流設計

## 驗收條件

- 全新安裝且沒有管理員時，系統會進入初始化模式
- 初始化頁面會顯示 `admin` 帳號與隨機初始密碼
- 第一個管理員可以成功登入
- 第一個管理員第一次登入後必須強制修改初始密碼
- 一般使用者可以用本機帳密登入
- 停權或停用的使用者無法登入
- 登出後目前的 authentication 狀態會失效
- 瀏覽器登入使用 `HttpOnly` cookie

## 未決問題

- 密碼複雜度是否要在最小長度之外加入額外規則
