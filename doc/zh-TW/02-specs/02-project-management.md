# 專案管理規格

## 目的

這份文件定義 KhaiKang 目前版本的專案管理功能規格。

目標是先建立一個可以運行起來、可以持續擴充的專案管理核心。
目前的流程骨架以 Kanban 為主，不先綁定 Sprint 流程。

## 範圍

目前規格涵蓋以下功能：

- 專案本體
- 專案成員
- 專案角色
- 專案設定
- Issue / Work item
- Issue 類型
- Issue 狀態
- 基本流轉
- 預留 AI 介面

## 非目標

目前不包含：

- Workspace 層級
- 完整議題管理產品相容性
- 複雜流程編排引擎
- 自訂工作流編輯器
- AI 自動執行
- 多專案組織樹狀管理

## 核心模型

### 專案

專案是第一階段的主要業務容器。

每個專案至少需要支援：

- 名稱
- 代號
- 描述
- 啟用 / 停用狀態
- 成員管理
- 專案層角色
- 基本設定

#### 專案基本資料

第一版專案本體至少要包含以下欄位：

- 名稱
- 代號
- 說明
- 狀態

其中：

- `名稱` 用於一般顯示
- `代號` 用於專案穩定識別，並作為 Issue 編號前綴
- `說明` 用於補充專案用途與範圍
- `狀態` 用於表示專案是否仍然啟用

#### 專案管理者

每個專案建立後，系統至少要有一位專案管理者。

第一版的專案管理者規則如下：

- 專案建立者可以被預設指定為專案管理者
- 專案管理者可以調整專案基本設定
- 專案管理者可以管理專案成員
- 專案管理者可以新增、修改、移除專案成員

第一版先只處理人員管理，不先開放更細的專案設定內容。

### 專案成員

同一個使用者可以加入多個專案。

成員關係至少要支援：

- 角色指派
- 存取範圍限制
- 狀態管理

第一版專案成員管理至少要支援：

- 新增成員
- 修改成員角色
- 移除成員

移除成員的意思是取消專案關聯，不是刪除使用者帳號。

### 專案角色

第一階段先提供預設專案角色：

- `Owner`
- `Manager`
- `Contributor`
- `Reviewer`

系統管理角色 `System Admin` 仍屬於系統層，不直接當作專案角色使用。

#### 流程定位

第一階段的實際流程骨架採 Kanban 思維：

- 不先綁定 Sprint
- 不先綁定固定節奏會議
- 不先綁定迭代承諾範圍
- Issue 以自由流轉為主
- 使用者與 AI 都可以在流程中被視為可追蹤的執行者

這表示：

- 流程實作先以 Kanban 方式落地
- 未來如果需要，再補 Sprint 與迭代功能

#### 角色原則

- `System Admin` 只負責系統層管理
- 專案角色只在指定專案內生效
- 專案成員加入時必須指定至少一個專案角色
- 同一個人可以在不同專案擁有不同角色
- 同一個人也可以在多個專案重複使用同一個角色
- `Owner` 只代表該專案內的最高權限，不代表整個系統的最高權限

#### 角色與成員關係

第一版先採用簡單的角色指派方式：

- 一個專案成員至少要有一個專案角色
- 一個專案成員可以被變更角色
- 一個專案成員可以被移除專案

第一版不先做複雜的角色繼承、角色模板或多層權限疊加。

#### 第一版角色責任範圍

`Owner`

- 管理專案基本資料
- 管理專案成員
- 指派與調整專案角色
- 建立、編輯、指派與完成 Issue

`Manager`

- 協助管理專案成員
- 建立、編輯、指派與完成 Issue
- 不負責專案最高權限管理

`Contributor`

- 建立與編輯自己可存取的 Issue
- 可調整處理人與狀態
- 參與日常工作項目處理

`Reviewer`

- 檢視與更新 Issue
- 可協助調整狀態與處理人
- 主要用於審查、確認與回饋

第一版先不把角色能力切得太細。
只要能支援專案建立、成員管理、Issue 建立與自由流轉即可。

### 專案設定

第一版的專案設定先只保留最小範圍。

目前至少包含：

- 專案基本資料
- 專案成員與角色管理

第一版先不處理以下進階設定：

- 自訂工作流規則
- 自訂角色建立
- 自訂欄位模板
- 自訂看板欄位映射
- 外部整合規則

### Issue / Work item

Issue 是專案中最基本的追蹤單位。

第一階段先支援：

- 建立
- 編輯
- 指派
- 狀態流轉
- 查詢

第一版的 Issue 流程原則如下：

- 狀態先不加限制
- 使用者可以自由切換 Issue 狀態
- 使用者可以自由更換下一手處理人
- 第一版先不做狀態轉移規則
- 第一版先不做審批式流程
- 後續若要加規則，再以設定方式擴充
- 第一版以 Kanban 式自由流轉為核心

#### 第一版 Issue 基本欄位

第一版的 Issue 至少要包含：

- 標題
- 類型
- 說明
- User Story
- Definition of Done
- 狀態
- 處理人
- 建立人
- 完成說明
- 建立時間
- 更新時間

其中：

- `處理人` 在第一次建立時預設為未指派
- `狀態` 在第一次建立時使用系統預設初始狀態
- `建立人` 與時間欄位必須由系統自動記錄
- `User Story` 主要提供需求型 Issue 使用
- `Definition of Done` 用來記錄該 Issue 被視為完成前應達成的條件
- `完成說明` 用來記錄實際完成內容與補充結果

#### 第一版 Issue 欄位規則

第一版先定義以下欄位規則：

- `標題` 為必填
- `類型` 為必填
- `說明` 可為空
- `User Story` 可為空，但對需求型 Issue 建議填寫
- `Definition of Done` 可為空，但建議在正式開始處理前補上
- `狀態` 為必填，但建立時由系統帶入預設值
- `處理人` 可為空，表示未指派
- `完成說明` 可為空，但在切換為完成狀態時建議填寫
- `建立人` 為系統自動帶入，不可由前端任意指定
- `建立時間` 為系統自動帶入
- `更新時間` 為系統自動更新

第一版先不納入以下欄位為必備欄位：

- 截止日
- 預估工時
- 實際工時
- 標籤
- 關聯 Issue
- 附件
- 自訂欄位

這些欄位後續若需要，可再逐步擴充。

#### Issue 完成定義

第一版先以狀態作為完成依據。

- 當 Issue 被切換到完成狀態時，視為該 Issue 已完成
- `Definition of Done` 是工作完成前的預期條件
- `完成說明` 是工作完成後的實際結果紀錄
- 第一版不額外要求審核通過、子任務全結束或測試關卡完成才可結案
- 後續若需要，再補更嚴格的完成條件

### Issue 類型與狀態

第一階段先提供預設值，後續可擴充成可自訂資料：

- Issue Type
- Status
- Priority

這些項目應以資料表與 seed 預設值實作，不以程式碼 enum 鎖死。

#### 第一版 Issue Type

第一版先提供以下預設類型：

- `story`
- `task`
- `bug`
- `spike`

這些類型已足夠支援一般敏捷開發與 Kanban 流程。

#### 第一版 Priority

第一版先提供以下預設優先級：

- `low`
- `medium`
- `high`
- `critical`

## 流程

### 專案建立

使用者建立專案後，系統應：

- 建立專案基本資料
- 套用預設專案設定
- 初始化預設角色與成員關係

### 成員加入

專案管理者可以將使用者加入專案，並指定角色。

專案成員管理至少要支援：

- 新增成員
- 修改成員角色
- 移除成員

### Issue 操作

使用者可以在專案中建立與管理 Issue。

最小操作流程：

- 建立 Issue
- 編輯 Issue
- 指派 Issue
- 更新狀態
- 查詢 Issue 清單

第一版的 Issue 操作規則如下：

- 建立 Issue 時，處理人預設為未指派
- 建立後可以再指定處理人
- 不同狀態下都可以變更處理人
- 不同狀態下都可以變更狀態
- 完成 Issue 時，以狀態切換完成為主

#### Issue 建立最小輸入

第一版建立 Issue 時，前端至少要提供：

- 標題
- 類型

以下欄位可選填：

- 說明
- 處理人

以下欄位由系統自動處理：

- 狀態
- 建立人
- 建立時間
- 更新時間

## 狀態與規則

### 專案狀態

專案至少要支援：

- `active`
- `inactive`

### Issue 狀態

第一階段先採用系統預設狀態，並保留未來擴充空間。

建議最小集合：

- `created`
- `in_progress`
- `verifying`
- `completed`

#### 第一版流轉原則

- 狀態轉移先完全放開
- 不限制 `created`、`in_progress`、`verifying`、`completed` 的移動方向
- 不限制同時變更負責人
- 不限制使用者是否直接指派給其他人
- 後續若需要，可再導入專案層級規則

#### 完成狀態

第一版先以 `completed` 作為明確完成狀態。

- `verifying` 代表驗證中
- `completed` 代表已完成

### 基本規則

- 專案成員才能操作該專案內的 Issue
- 系統管理者可以管理全站層級資料
- 專案角色只在指定專案內生效
- AI 介面先預留，不在第一階段自動執行
- Issue 第一版先採自由流轉，不設轉移門檻
- 專案角色第一版只允許使用系統預設角色

## 安全與稽核

專案管理相關操作必須可稽核。

至少要記錄：

- 專案建立
- 專案更新
- 專案停用
- 成員加入
- 成員移除
- 角色變更
- Issue 建立
- Issue 更新
- Issue 狀態變更

所有稽核紀錄都必須能對應到 `actor_id` 與 `actor_type`。

## 驗收條件

- 使用者可以建立專案
- 使用者可以加入專案成員
- 專案可以指定預設角色
- 使用者可以建立 Issue
- 新建立的 Issue 預設為未指派
- 建立 Issue 時至少可只輸入標題與類型
- 使用者可以變更 Issue 狀態
- 使用者可以在任意狀態下更換處理人
- 使用者可以將 Issue 切換為完成狀態
- 系統可以保留未來自訂 Issue 類型與狀態的空間
- 系統不需要 Workspace 也能正常運作

## 未決問題

- Issue 是否要先支援 comment
- Issue 是否要先支援 tag
- Issue 是否要先支援 parent / sub-task
- `verifying` 是否需要再細分驗證責任或驗證結果類型
